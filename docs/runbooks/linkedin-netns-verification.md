# Проверка резидентного выхода LinkedIn

Спека: `docs/superpowers/specs/2026-08-09-linkedin-source-recovery-design.md` (репозиторий `hermes`).

Процедура выполняется один раз после настройки пира и содержит **сутки ожидания**
на шаге 5. Шаг, чей результат не совпал с ожидаемым, останавливает процедуру:
идти дальше по сломанной конструкции бессмысленно, а каждый вход в LinkedIn —
рисковое событие, которое нельзя тратить впустую.

## Предусловия на стороне Firewalla

Выполняет владелец в приложении:

1. Пир для VPS в `VPN Server → WireGuard → Setup`.
2. Правила per-peer: выход этого пира прибит к резидентному WAN. На границе два
   WAN с разными next hops; плавающий выходной адрес хуже стабильного чужого,
   потому что смена адреса посреди сессии для LinkedIn — сигнал компрометации.
3. Доступ этого пира внутрь LAN запрещён. VPS несёт агента, исполняющего задачи
   из мессенджеров, и открыт наружу по SSH: туннель, дающий ему LAN, превращает
   компрометацию VPS в присутствие в homelab.

Конфигурация пира кладётся на VPS в `/etc/wireguard/wg0-ln.conf` с правами `600`,
владелец `root`. В репозиторий она не коммитится.

## 1. Поднять namespace

    sudo LINKEDIN_WG_ADDR=<адрес пира> bash scripts/linkedin-netns-up.sh

Ожидается строка `netns ln-eg поднят`. Скрипт сам проверяет, что маршрут по
умолчанию единственный и идёт через `wg0-ln`; если это не так, он завершается с
кодом 1 и ничего не запускает.

## 2. Проверить три молчаливых отказа по отдельности

Все три при поломке дают правдоподобный результат, а не ошибку, поэтому каждый
проверяется своей командой. Вывод «браузер открылся, значит работает» здесь
недопустим.

**Внешний адрес изнутри namespace:**

    sudo ip netns exec ln-eg curl -s https://api.ipify.org

Ожидается домашний адрес. Датацентровый адрес означает неправильно собранный
маршрут — останов.

**Резолвер внутри namespace:**

    sudo ip netns exec ln-eg getent hosts www.linkedin.com

Ожидается ответ. Пустой означает, что Firewalla не раздал резолвер своим
WireGuard-клиентам: открыть точечное правило на `<PIHOLE_IP>:53` (udp и tcp) —
именно одно правило на один адрес, а не доступ в LAN — и повторить.

**Ассеты LinkedIn не заблокированы фильтром:**

    sudo ip netns exec ln-eg getent hosts static.licdn.com

Ожидается адрес. `NXDOMAIN` означает, что Pi-hole режет ассеты: страница
отрендерится частично, экстрактор увидит ноль карточек, и это будет прочитано
как антибот-детект. Добавить в allowlist и повторить.

## 3. Ручной вход

    sudo bash scripts/browser-desktop-linkedin.sh

Chromium, Xvfb, x11vnc и noVNC поднимутся уже внутри namespace. noVNC слушает на
управляющем veth-адресе `169.254.77.2`, а не на `127.0.0.1`: внутри netns
loopback свой собственный и из SSH-туннеля недостижим. Туннель поэтому такой:

    ssh -L 6080:169.254.77.2:6080 hermes

Пароль VNC:

    sudo cat /var/lib/browser-desktop/.vnc/password.txt

Открыть `http://127.0.0.1:6080/vnc.html`, войти в LinkedIn, дождаться полной
загрузки ленты и открыть `https://www.linkedin.com/jobs/`.

Вход, выполненный вне namespace, обесценивает всю проверку и расходует рисковое
событие впустую.

## 4. Зафиксировать состояние сразу после входа

    sudo ~/.hermes/hermes-agent/venv/bin/python -m job_intel.linkedin_readout \
      --profile /var/lib/browser-desktop/profiles/linkedin --json

Ожидается `"session_state": "session_ok"` и `li_at` в списке куки. Записать вывод
в журнал проверки — он понадобится для сравнения на шагах 5 и 7.

## 5. Сутки контрольной тишины

Никакой автоматической активности. Через 24 часа повторить шаг 4.

Это контрольная группа, и в этом её единственный смысл. Если `li_at` умирает при
нулевой автоматизации, причина не в поведении скрапера, и гипотезу о географии
надо проверять дальше уже без этой ветки. У решения от 2026-07-04 такого
измерения не было — поэтому его вывод о причине был интерпретацией, а не
измерением.

## 6. Один контролируемый прогон

    sudo ip netns exec ln-eg env PYTHONPATH=/home/hermes/.hermes/hermes-agent \
      ~/.hermes/hermes-agent/venv/bin/python -m job_intel.cli --sources linkedin --dry-run

## 7. Замеры

Повторить шаг 4 через 30 минут, 2 часа и 24 часа после шага 6.

## Условия остановки

- **Жёсткий челлендж на шаге 3** (капча, запрос документа): остановиться, повторно
  не проходить, вернуться к пересмотру плана. Многократное прохождение таких
  проверок и есть та эскалация, ставка в которой — основной профиль владельца.
- **Смерть куки на шаге 7** при корректном адресе на шаге 2: гипотеза о географии
  опровергнута, фазу A не начинать.

## Критерий выхода

`linkedin` возвращается в `JOB_INTEL_ENABLED_SOURCES` (`/etc/job-intel/job-intel.env`)
только после чистых результатов шагов 5 и 7. Ни одна задача плана этого не делает —
это отдельное действие оператора.
