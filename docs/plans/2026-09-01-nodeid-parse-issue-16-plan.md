## 0. Инвентаризация предпосылок

Правило 1.2: отсутствующие transport, persistence, identity, deployment и result
semantics — часть объёма, а не «сантехника на потом».

| Предпосылка | Состояние на `8dc8a8c48d` | Следствие для плана |
|---|---|---|
| **transport** | новых нет: раннер и гейт общаются argv, stdout и JSON-файлом | новых границ не появляется; composition проверяется настоящим subprocess-прогоном, а не подделанным выводом |
| **persistence** | node-report: `schema_version`, `files`, `collected_nodeids`, `failed_nodeids`, `collection_error_paths`, `error_count`, `tests_collected`, `skipped_paths`, `collect_ok`, `probe_ok`, `readable` (спека §3) | форма отчёта не меняется, меняется только содержимое `*_nodeids`; `schema_version` не трогаем |
| **identity** | не затрагивается | — |
| **deployment** | `scripts/acceptance/publish-runtime.sh` **dry-run only** по построению; `RUNTIME_FILES` (строка 19) перечисляет восемь файлов, `run_tests_parallel.py` среди них нет; `~/.hermes/scripts/` вне git и разошёлся с чекаутом (спека §2.4, §2.5) | публикация доказывается только композиционно (dry-run); реальная синхронизация хоста вынесена в deferred, статус хоста — `runtime not published` |
| **result semantics** | «раздутый узел → exact probe не собирает → `readable: false` → `unreadable_runs` → landing запрещён» (`scripts/upstream-sync-finalize.sh:770-782`) | это и есть инвариант, который закрепляет слайс 2 |

Операционные предпосылки прогонов — не часть патча, но часть выполнимости плана:

1. Прогоны идут под пользователем `hermes` (`ssh hermes-agent`), не под root:
   `~`-раскрытие и `Path.home()` в тестах иначе врут.
2. Интерпретатор — `./venv/bin/python` из чекаута.
3. **Полный `pytest` по дереву на этом хосте запускать нельзя**: loadavg уходит
   за 50 и systemd-вотчдог убивает живой гейтвей. Checkpoint §4 гоняет восемь
   именованных наборов, а не всё дерево.
4. `pytest-timeout` в венве **нет**, `--timeout=` не работает. Ограничение —
   внешний `timeout <N>` вокруг команды.
5. Живой чекаут переписывается резидентным агентом (`reset --hard` посреди
   сессии). Реализация ведётся в отдельном worktree; живой прогон из
   `~/.hermes/hermes-agent` выполняется **на зафиксированной ревизии после
   коммита**, и на время прогона в чекауте один writer (правило 3.1).
6. Живой прогон обязан идти из чекаута, а не из `~/.hermes/scripts/`. Переменные,
   которыми хостовый путь подменяет исполняемые файлы — `HERMES_SYNC_TEST_CMD`,
   `HERMES_UPSTREAM_SYNC_GATE`, `HERMES_FORK_TEST_RUNNER` — фиксируются в
   протоколе прогона явно, иначе непонятно, что именно измерено.

## 1. Как §5 спеки превратилась в три слайса и один checkpoint

Спека даёт десять задач. Задачи 1, 5, 6, 8 и 10 сами по себе наблюдаемого
результата не дают. Правило 1.4: задача, добавляющая только слой, тестовую
матрицу или отметку, принадлежит срезу, который её доказывает. Правило 1.5:
safety-инвариант описывается **внутри владеющего среза**, а не отдельным циклом
доставки. Отсюда три слайса плюс acceptance/handoff checkpoint.

| Задача спеки | Куда попала |
|---|---|
| 1. Модуль общего разбора | слайс 1 |
| 2. Раннер на общее правило | слайс 1 |
| 6. Миграция переносимости bundle | слайс 1, тот же коммит (спека §4: «обязана ехать в одном коммите с задачей 2») |
| 7. Живой синтетический прогон | разрезана: дверь node-report → слайс 1, обе двери → слайс 2 |
| 3. Гейт на общее правило | слайс 2 |
| 5. Тест паритета дверей | слайс 2 |
| 10. Fail-closed regression | слайс 2 (владеющий срез: правило уже стоит в обеих дверях) |
| 4. `measure_order_leakage` | слайс 3 |
| 8. Обязательный набор зелёный | checkpoint §4 — не слайс |
| 9. Синхронизация `~/.hermes/scripts/` | deferred §5, отдельное разрешение |

Задача 7 разрезана намеренно: правило 2.7 требует realistic smoke **сразу после
первого вертикального среза**, а не в конце. Держать весь живой прогон в конце
означало бы два слайса подряд без runtime proof.

Порядок исполнения: слайс 1 → слайс 2 → слайс 3 → checkpoint. Слайс 3 независим
от слайса 2 и может идти раньше него, но не раньше слайса 1.

## 2. Слайс 1. Раннер даёт гейту два различных узла; bundle атомарно готов к публикации

**Наблюдаемый результат.** На параметризации `alpha - old` / `alpha - new` живая
цепочка из чекаута — раннер → node-report → `upstream_sync_gate.py node-outcome
--node-report` → `new-failures` → `classify-node-failures` — доносит **два
различных** узла и выдаёт по новому отказу блокирующий вердикт вместо тихого
`pre_existing_failure`. Комплект «раннер + helper» переносим и композиционно
готов к публикации.

Заголовок сознательно не говорит «опубликован»: публикация здесь доказывается
только dry-run'ом, реальный хост остаётся старым (§5.1). Статус хоста после
слайса — `runtime not published`.

**Из спеки.**
§5.1: «сначала `tests/scripts/test_pytest_status_lines.py` — таблица
поддерживаемого класса из §3 … Затем `scripts/pytest_status_lines.py` с
`parse_status_line(line) -> StatusLine | None` на балансном скане».
§5.2: «строки 585–598: набор статусов и `partition` уходят в `parse_status_line`,
`SKIPPED` идёт в `_parse_skipped_path` через `value`».
§4: «задача 6 — не строчка, а миграция публикации runtime, и она обязана ехать в
одном коммите с задачей 2, иначе между ними существует состояние, где
опубликованный раннер не стартует».
§1: «Схлопнутые узлы означают, что `compare_test_outcomes` не видит нового
падения, а `classify_node_failures` метит его `pre_existing_failure`».

**Состав патча — один коммит.**

1. `tests/scripts/test_pytest_status_lines.py`: таблица поддерживаемого класса

   `SKIPPED` со сводкой пути, дефис без пробелов, пустая строка) и два **отдельно

2. `scripts/pytest_status_lines.py`: `StatusLine(status, nodeid, detail, value)`

5. Переносимость bundle, пять проверок §5.6, каждая отдельным тестом:

   - dry-run публикации доказывает, что раннер и helper уезжают вместе с гейтом

   - раннер и гейт стартуют из произвольного cwd без repo-root в `sys.path`;
   - **неполный bundle падает до тестового прогона** с внятной ошибкой, а не

**RED → GREEN.**

| Что | RED, ожидаемая причина | GREEN |
|---|---|---|
| helper | `ModuleNotFoundError` — модуля ещё нет | 14/14 входов класса разобраны верно, включая `test_case[a[b] - inner]` и `test_r[range[0:3] - lo]` |

**Mutation-проверка** (правило 2.3 — граница, где ложный green **скрывает отказ**):
возврат `partition(" - ")` в строку 598 обязан ронять новый тест раннера. Это
единственная mutation в плане; на остальной проводке она не ритуал.

**Лестница проверок.** Focused (helper, раннер) → owning suites
(`tests/test_run_tests_parallel.py`, `tests/scripts/test_pytest_status_lines.py`,

## 3. Слайс 2. Обе двери равны, и известный отказ разбора остаётся блокирующим

**Наблюдаемый результат.** На одном живом выводе раннера лог-дверь
(`node-outcome --log --aggregate`) и дверь node-report (`node-outcome
--node-report`) дают равные списки узлов, и в них два элемента — буквальный текст
acceptance criteria issue #16. Одновременно раздутый селектор, который балансный
скан может произвести на неподдерживаемом входе, доказанно упирается в
блокирующий вердикт, а не проходит тихо.

**Внутренний порядок** — регрессия пишется против уже мигрированной цепочки, а не
против половины: гейт на общее правило → матрица паритета → fail-closed regression.

**Из спеки.**
§5.3: «тест на `parse_test_outcomes` с тем же входом (два узла) и такой же в
агрегатном режиме, со строками в рамке `║`, чтобы снятие рамки осталось
покрытым … фильтры двери (`path.endswith(".py")`, отказ на `":" in path`, набор
статусов с `RERUN`) сохраняются на месте вызова».
§5.5: «Требование: списки узлов лог-двери и node-report двери равны и содержат два
элемента».
§5.10: «Балансный скан выбран за направление отказа (§3), значит это направление
обязано быть закреплено тестом, а не остаться свойством текущего кода… **Запрещено**
… нормализовать это до пустого успешного probe и фильтровать request **до**
merged-isolated прогона».
§3: «Fail-closed держится ровно на том, что merged-isolated probe идёт **раньше**
и его unreadable не теряется. Этот порядок — часть контракта, а не деталь
реализации».

**Состав патча.**

1. `tests/scripts/test_upstream_sync_gate.py`: два теста на `parse_test_outcomes`
   (`scripts/upstream_sync_gate.py:1076`) — обычный режим и агрегатный со строками
   в рамке `║`, которая срезается около строки 1097.
2. `scripts/upstream_sync_gate.py:961-971`: тело `_nodeid_from_status_line`
   заменяется вызовом `parse_status_line`. Набор статусов
   `{PASSED, FAILED, XFAIL, XPASS, RERUN, ERROR}`, `path.endswith(".py")` и отказ
   на `":" in path` остаются **на месте вызова**.
3. `_READABILITY_MATRIX` в `tests/scripts/test_upstream_sync_gate.py`: новый
   сценарий с падающей setup-фикстурой и параметрами `alpha - old` / `alpha - new`;
   `assert len(_READABILITY_MATRIX) == 16` становится `== 17`.
4. Fail-closed regression на раздутый селектор (непарная `[` в payload) — новый
   файл `tests/scripts/test_nodeid_fail_closed.py` либо секция в наборе гейта,
   решается при реализации. Тест проводит селектор по пяти звеньям:
   1. раздувается и **проходит** `_looks_like_nodeid`
      (`scripts/run_tests_parallel.py:526` смотрит только на часть до первого `::`);
   2. попадает в `build_upstream_probe_request` — проверка по манифесту тоже
      смотрит только путь;
   3. merged-isolated exact probe его не собирает: pytest rc=4 `ERROR: not found`,
      раннер rc=1, node-report с `readable: false`, `tests_collected: 0`;
   4. `node-outcome --node-report` падает с rc=2 и текстом
      `run_tests_parallel node report is unreadable`
      (`scripts/upstream_sync_gate.py:1397`);
   5. классификация даёт `unreadable`/`unknown`, landing запрещён
      (`scripts/upstream-sync-finalize.sh:770-782` складывает `unknown` и
      `unreadable_runs` и отказывает при ненулевой сумме).
5. Живой прогон обеих дверей на одном выводе раннера из чекаута — вторая половина
   §5.7.

**RED → GREEN.** Оба теста `parse_test_outcomes` и матричный сценарий падают до
правки гейта, показывая один узел `tests/test_dash.py::test_case[alpha`. После —
два узла и равенство списков.

Fail-closed regression — особый случай: он зелёный на текущем коде, потому что
фиксирует свойство, а не чинит дефект. Его доказательство — не RED до правки, а
**два отката**, каждый из которых обязан его ронять:
откат A — фильтрация request **до** merged-isolated probe;
откат B — нормализация unreadable в пустой успешный probe.
Без обоих откатов тест не считается закрывающим §5.10.

**Лестница проверок.** Focused (две двери) → owning suites
(`tests/scripts/test_upstream_sync_gate.py`,
`tests/scripts/test_upstream_sync_finalize.py`) → composition (матрица с живым
раннером внутри, цепочка раздутого селектора) → runtime (прогон обеих дверей из
чекаута).

**DoD.**

      команда, exit и **фактический** схлопнутый узел из вывода (`expected_red`).

## 5. Acceptance/handoff checkpoint — не слайс

Правило 2.4: полный gate запускается **один раз** на готовый macro-slice или
handoff. Правило 1.4 запрещает делать из этого отдельный delivery cycle: своего
патча checkpoint не производит, его артефакт — доказательство.

Запускается один раз на **неизменяемом candidate** после последнего кодового
слайса. Если gate находит дефект, исправление возвращается **во владеющий срез**
и создаётся новый candidate; checkpoint прогоняется заново на нём.

**Из спеки.** §5.8: «Восемь файлов, не пять: gate, runner, sync-local, selection
(отдельной строкой, точный venv), finalize, apply, triage, slack. Покрытие считать
**по имени** упавшего теста, никогда по счётчику:
`TestRepoLock::test_rebase_script_refuses_to_run_while_repo_lock_is_held` падает
всегда (ownership repair срабатывает раньше проверки lock), и „1 failed“ в
finalize — норма, а не сигнал».

**Состав.**

Восемь обязательных наборов:

1. `tests/scripts/test_upstream_sync_gate.py`
2. `tests/test_run_tests_parallel.py`
3. `tests/scripts/test_sync_local_customizations.py`
4. `tests/scripts/test_run_fork_tests_selection.py` — отдельной строкой, точный venv
5. `tests/scripts/test_upstream_sync_finalize.py`
6. `tests/scripts/test_upstream_sync_apply.py`
7. `tests/scripts/test_upstream_sync_triage.py`
8. `tests/scripts/test_upstream_sync_slack.py`

Плюс три набора, созданные или изменённые планом:
`tests/scripts/test_pytest_status_lines.py`,
`tests/scripts/test_measure_order_leakage.py`,
`tests/scripts/test_acceptance_publish_runtime.py`.

**Критерии прохождения.**

- [ ] Все прогоны — на **одной** ревизии-кандидате; SHA записан и совпадает во всех
      протоколах (правило 5.6).
- [ ] Рабочее дерево на момент прогона чистое; `git status --porcelain` записан.
- [ ] Каждый прогон имеет финальную строку pytest со счётчиками и exit. Прогон без
      неё — `unreadable_or_killed`, а не green (правило 4.2), и повторяется с
      внешним `timeout`.
- [ ] Каждое падение названо **по имени теста**; ни одно суждение не сделано по
      счётчику.
- [ ] `TestRepoLock::test_rebase_script_refuses_to_run_while_repo_lock_is_held`
      (`tests/scripts/test_upstream_sync_finalize.py:571`) назван известным
      baseline failure и отделён от новых (правило 4.4).
- [ ] Список падений сверен с baseline на `8dc8a8c48d`: новых имён нет. Каждое
      новое, если появилось, отнесено ровно к одной категории §8 правил и
      возвращено во владеющий слайс.
- [ ] Полный `pytest` по дереву **не** запускался (§0.3); это сказано в протоколе
      явно, чтобы отсутствие полного прогона не выглядело упущением.
- [ ] Evidence packet заполнен целиком по форме §6, включая `known_limitations`
      (два ограничения разбора из §3 спеки), `working_tree_state` и
      `pending_authority_or_decisions` (публикация в `~/.hermes/scripts/`).
- [ ] Таблица §7 плана перепроверена построчно: каждый критерий issue назван
      закрывшим его слайсом и ссылкой на конкретное доказательство.
- [ ] Итоговый статус: `composition_verified` для чекаута,
      `deployed_not_verified` для хоста. `complete` **не** ставится — живой синк
      исполняет старые копии до отдельного разрешённого publish (спека §5.9).

**Открытый пункт для владельца: где живёт evidence packet.** Пакет обязателен как
артефакт; форму доставки выбирает владелец. У обоих вариантов разные последствия
для семантики snapshot, и они названы здесь, чтобы открытый пункт не прятал drift
ревизии.

*Вариант A — пакет остаётся внешним отчётом владельцу.* Проверенный candidate
остаётся неизменным, HEAD после checkpoint не двигается. Проще и без оговорок.

*Вариант B — пакет коммитится в `docs/evidence/…` одним handoff-коммитом*
(правило 3.6 допускает такое пакетное обновление). Тогда HEAD после checkpoint
меняется, и новый SHA **нельзя молча называть проверенным candidate**: правило 5.6
требует совпадения candidate revision с проверенной. Обязательно:

- [ ] в пакете раздельно записаны `tested_candidate_revision` и
      `evidence_commit_revision`;
- [ ] доказано, что diff между ними содержит **только** `docs/evidence/…`
      (`git diff --name-only <tested> <evidence>` приложен);
- [ ] нигде не утверждается, что восемь наборов выполнялись на evidence-коммите;
- [ ] если политика приёмки требует принимать именно финальный HEAD — checkpoint
      прогоняется заново на нём, и это новый gate, а не переиспользование старого.

## 8. Форма evidence packet

Правило 4. Заполняется на handoff слайсов 1, 2 и на checkpoint.

```text
objective:
authorized_scope:
explicit_deferrals:
base_revision:
candidate_revision:
changed_paths:
red_evidence: command, exit, expected failure
green_evidence: command, exit, relevant count/assertion
composition_evidence:
runtime_evidence:
full_gate_evidence:
known_limitations:
working_tree_state:
pending_authority_or_decisions:
```

Что здесь особенно легко нарушить именно в этой работе:

- команда без финального exit/result receipt — не evidence;
- `0 tests`, пустой node-report, killed process, unreadable output — не green;
- если runtime не проверялся, писать `runtime not verified`, а не выводить его
  состояние из unit-тестов;
- dry-run публикации — **не** runtime proof публикации; хост после всех трёх
  слайсов остаётся `runtime not published`.

## 9. Stop conditions

Помимо общих (правило 10), останавливаться и спрашивать владельца, если:

- живой чекаут `~/.hermes/hermes-agent` изменился между коммитом и прогоном
  (резидентный агент сделал `reset --hard`) — acceptance snapshot уехал;
- выяснилось, что живой синк исполняет не чекаут, а хостовую копию, и результат
  прогона относится не к той ревизии;
- потребовалось поменять порядок «merged-isolated probe раньше upstream
  availability filter» ради прохождения теста — это меняет trust boundary
  (спека §3), а не деталь реализации;
- потребовалось расширить поддерживаемый класс разбора, чтобы что-то прошло;
- прогон набора завершился без финальной строки pytest — это
  `unreadable_or_killed`, повторять с внешним `timeout`, а не считать зелёным;
- для продолжения нужна публикация в `~/.hermes/scripts/` — отдельная авторизация
  (§6.1).

## 10. Что было спорно между Claude и Codex и чем кончилось

1. **Пять слайсов или три.** Claude предложил пять, отдельными срезами на задачу
   10 и на задачу 8. Codex возразил: задача 10 test-only и сама нарушает правило
   1.4, а восемь наборов — не срез, а handoff-gate по правилу 2.4. Принято
   возражение; сильнее того, правило 1.5 говорит буквально, что safety-инвариант
   описывается внутри владеющего среза. Задача 10 ушла в слайс 2, задача 8 стала
   checkpoint без своего патча.
2. **Достаточно ли двери node-report для первого среза.** Codex: честный
   вертикальный срез, но только если результат проведён до решения гейта
   (`node-outcome` → `new-failures` → `classify-node-failures`), потому что сам
   JSON — промежуточный артефакт. Принято, DoD слайса 1 усилен. Оговорка Claude
   записана в DoD: baseline для `new-failures` в слайсе 1 синтетический, и это
   подмена внешнего входа, а не проверяемого стыка.
3. **Заголовок «публикуется целиком».** Codex: завышено, задача 6 доказывает
   только dry-run/composition публикации. Принято, заголовок и статус переписаны
   на `publication composition verified` / `runtime not published`.
4. **Заголовок слайса про `measure_order_leakage`.** Codex: «третья копия правила
   исчезает» описывает слой, а не срез. Принято, заголовок назван по наблюдаемому
   результату, а инвариант ушёл внутрь DoD.
5. **Коммит evidence packet.** Codex предлагал формировать пакет без отдельного
   коммита. Claude возразил: правило 3.6 допускает один пакетный doc-коммит на
   handoff, и пакет — самостоятельное аудируемое решение. Не разрешено ни в чью
   пользу: пакет обязателен как артефакт, форма доставки оставлена решением
   владельца. Codex добавил к этому обязательное последствие, которого не было ни
   у кого: коммит пакета двигает HEAD, и новый SHA нельзя молча называть
   проверенным candidate (правило 5.6). Оба варианта развилки с их последствиями
   выписаны в §5.
6. **Разрешение на запись.** Codex отдельно оговорил, что его согласие относится
   к содержанию структуры и не является разрешением писать файл или коммитить.
   Верно и записано: авторизация на сохранение и коммит этого документа получена
   от владельца, авторизация на **реализацию** плана — нет (см. таблицу вверху).
