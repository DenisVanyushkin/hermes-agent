# Инженерные футеры и аудитория канала

Три футера конца хода адресованы ревьюеру кода, а не адресату сообщения:

1. блок «Где выполнялись проверки» (`hermes_cli/run_evidence.py`) — где
   физически исполнялись команды хода;
2. отчёт о неудавшихся записях файлов (`display.file_mutation_verifier`);
3. объяснялка оборванного хода (`display.turn_completion_explainer`).

Кому их не показывать, решают ДВА независимых механизма: список платформ (для
живых каналов) и аудитория задания (для крона). Один не заменяет другой —
см. «Крон» ниже.

## Живые каналы: список платформ

`display.suppress_engineering_footers_platforms` — список платформ, на которые
эти три футера не уходят. На перечисленных каналах объяснялка оборванного хода
не убирается совсем, а заменяется одной нейтральной русской строкой: молчание
в чате читается как «меня проигнорировали». Строка не зовёт повторить просьбу —
ход мог отработать наполовину, и повтор на пути бытового CRUD положил бы
позицию в список второй раз; она предлагает проверить результат.

По умолчанию список пуст — поведение прежнее на всех каналах.

```yaml
display:
  suppress_engineering_footers_platforms: [whatsapp]
```

Значения сравниваются без учёта регистра и пробелов. Любая порча значения
(строка вместо списка — типично при потерянном тире; ошибка чтения конфига)
означает «не подавлять»: сломанный конфиг обязан давать лишние подробности
оператору, а не тихо выключать анти-оверклейм. Обе формы порчи пишут
`logger.warning` один раз на процесс — иначе единственным симптомом остаётся
«футеры всё ещё приходят». Отсутствие ключа и пустой список — не порча, они
молчат.

Платформа хода берётся по порядку: контекст сессии
(`HERMES_SESSION_PLATFORM`, выставляется гейтвеем на каждый ход) → атрибут
`agent.platform`. Контекст выше атрибута намеренно: у субагента, порождённого
внутри хода, свой агент, но адресат тот же самый.

## Крон: аудитория задания

**Писать `cron` в список платформ не нужно и нельзя.** У крона канал ХОДА и
адресат ДОСТАВКИ — разные вещи. Ход не выполняется ни на какой платформе
(`platform=""` в контексте сессии, `platform="cron"` у агента), а результат
уходит туда, куда указывает `deliver:` задания. Строка `cron` в списке
выключила бы футеры сразу у ВСЕХ заданий, включая операторские, где
анти-оверклейм и нужен.

Вместо этого крон использует уже существующий механизм аудитории
(`resolve_cron_audience` в `cron/scheduler.py`): явное поле `audience` на
задании, а если его нет — сеть безопасности `cron.end_user_targets`.

```yaml
cron:
  end_user_targets:
    - whatsapp:+77011102626
```

`run_job` кладёт резолвнутую аудиторию в контекстную переменную
`HERMES_CRON_AUDIENCE` на время задания и снимает её в `finally` (иначе
признак протёк бы в соседнее задание того же процесса). Конец хода читает её
по имени — `hermes_cli/run_evidence.py` не импортирует планировщик, чтобы не
втягивать его в турн-путь.

На задании с аудиторией `end_user` первые два футера не приклеиваются.
**Объяснялка оборванного хода на cron-ходе НЕ подменяется** — и это не
недоделка. `run_job` опознаёт аномально пустой ход сравнением на равенство с
текстом того же форматтера:

```python
final_response.strip() == AIAgent._format_turn_completion_explanation(
    turn_exit_reason
).strip()
```

и на совпадении обнуляет ответ, чтобы задание не доставило ничего. Подставь
туда другую строку — равенство перестанет выполняться, и вместо тишины
конечный пользователь получит «Ответ мог оборваться…», а прогон будет помечен
успешным. Поэтому на кроне подавление останавливается на футерах: тишину даёт
планировщик, и её нельзя ломать.

Про отказ прогона аудитория решает отдельно и раньше — см.
`plan_cron_failure_delivery`: заданию с `end_user` технический текст отказа не
доставляется вовсе, а оператор получает алерт в `gateway.error_alerts.channel`.

## Что это НЕ закрывает

На части сбойных ходов телом ответа становится англоязычная заглушка более
глубокого слоя (`⚠️ Provider authentication failed.`, `⚠️ Session too large
for the model's context window.`). Это не футер, и ни один из двух механизмов
на неё не влияет.

Операторский алерт (`gateway.error_alerts.channel`) на футеры не завязан:
`gateway/turn_error_alerts.py` классифицирует деградацию по собственным
префиксам и флагам результата. Подавление футеров алерт не глушит.
